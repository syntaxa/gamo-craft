# Policy: Изменения требований и документация

## Цель
Любое изменение требований к продукту, MVP, UX, геймплею, экономике, наградам, обучению или платформенным ограничениям должно сразу отражаться в документации проекта.

## Обязательное правило
Изменение требований **не считается завершенным**, пока не обновлены релевантные документы.

Документы проекта должны описывать текущее состояние продукта и архитектуры. Нельзя добавлять журналы изменений, changelog-блоки или датированные секции вида `Update ...`; изменения нужно вносить прямо в тело соответствующих разделов. История изменений хранится в Git.

## Минимальный набор документов
При изменении требований проверяются и при необходимости обновляются:
- `docs/requirements-registry.md`
- `docs/concept.md`
- `docs/architecture.md`
- `docs/technical-design.md`
- `docs/testing.md` (если меняются инварианты, сценарии или критерии проверки)

## Матрица соответствия
- Канонический список `REQ-*`: `docs/requirements-registry.md`
- Учет реализации `REQ-*`: раздел `Учет реализации` и `Матрица реализации` в `docs/requirements-registry.md`
- Изменения продуктовой логики и фич: `docs/concept.md`
- Изменения модулей, эпиков, DoD, MVP scope: `docs/architecture.md`
- Изменения API, моделей данных, событий, storage, спринтов: `docs/technical-design.md`
- Изменения тестируемых инвариантов и сценариев: `docs/testing.md`

## Учет реализации требований
Для каждого требования различаются:
- статус требования: актуальность для продукта (`ACTIVE`, если не указано иное);
- статус реализации: состояние подтверждения по текущему коду и тестам.

Статусы реализации:
- `IMPLEMENTED` — требование реализовано в коде; для критичного поведения есть тест или явная ссылка на источник реализации.
- `PARTIAL` — реализована только часть требования или нет достаточного покрытия для полного утверждения.
- `NOT_IMPLEMENTED` — в коде и тестах не найдено реализации, либо текущая реализация противоречит требованию.
- `UNKNOWN` — требование продуктового/качественного характера не удалось надежно подтвердить по коду и тестам.

Матрица реализации хранится в `docs/requirements-registry.md`, чтобы рядом с каноническим списком требований было видно, какие `REQ-*` уже закрыты, какие требуют доработки, и какими файлами это подтверждается. Доказательства должны ссылаться на стабильные источники: код, каталоги контента, unit/component/e2e тесты, scripts или конфигурацию. Для `IMPLEMENTED` предпочтительно указывать тест; если теста нет, в доказательстве явно указывается файл реализации.

## Процедура внесения изменений
1. Определить актуальное целевое состояние требования.
2. Обновить `docs/requirements-registry.md`.
3. Проверить, меняется ли статус реализации требования по коду и тестам; при необходимости обновить `Матрицу реализации` в `docs/requirements-registry.md`.
4. Если требование помечается как `IMPLEMENTED`, добавить или указать доказательство: тест, код реализации, каталог контента, script или конфигурацию.
5. Синхронизировать затронутые документы по месту, в теле соответствующих разделов.
6. Добавить в описание PR раздел `Requirements Change`.
7. В этом разделе перечислить обновленные файлы и кратко, что именно синхронизировано.

Не нужно дословно дублировать `REQ-*` во всех документах: реестр хранит точные требования, остальные документы описывают их на своем уровне.

## Обязательный формат секции в PR
```md
## Requirements Change
- Change: <кратко, что изменилось в требованиях>
- Updated docs:
  - [ ] docs/requirements-registry.md
  - [ ] docs/concept.md
  - [ ] docs/architecture.md
  - [ ] docs/technical-design.md
  - [ ] docs/testing.md (if applicable)
- Notes: <что именно синхронизировано>
```

## Правило отклонения
PR/изменение должно быть отклонено, если:
- требования изменены, но документация не обновлена;
- статус реализации в реестре не соответствует коду или тестам;
- требование помечено как `IMPLEMENTED`, но в матрице нет доказательства;
- требования добавлены только в changelog/датированный блок, а тело документа осталось устаревшим;
- документы противоречат друг другу;
- MVP scope в `docs/architecture.md` и `docs/technical-design.md` расходится с `docs/concept.md`.

## Definition of Done (для изменений требований)
Изменение требований считается завершенным только если:
1. Код (если был) обновлен.
2. Документация синхронизирована.
3. Матрица реализации в `docs/requirements-registry.md` отражает фактическое состояние затронутых `REQ-*`.
4. Для новых `IMPLEMENTED`-статусов указаны доказательства.
5. В PR заполнен checklist по документации.
6. Нет противоречий между `docs/concept.md`, `docs/architecture.md`, `docs/technical-design.md`.
7. Нет changelog/датированных `Update ...`-секций.
