# Стратегия автоматического тестирования

## 1. Цели
- Защитить ключевой цикл MVP: `урок -> кото-монетки -> яйца -> FPV-строительство -> сохранение`.
- Быстро ловить регрессии в экономике, генерации заданий, луте и сохранениях.
- Поддерживать предсказуемую скорость разработки (быстрые unit, стабильные e2e).

## 2. Принципы
- Пирамида тестов: много unit, меньше component/integration, немного критичных e2e.
- Детерминизм: рандом, время и источники ID должны контролироваться в тестах.
- Проверка инвариантов домена важнее визуальных деталей.
- E2E покрывают только критичные сквозные сценарии и устройства.
- Запрещено подменять функционал проекта имитациями там, где тест может вызвать реальный код проекта.

## 3. Слои тестирования
## 3.1. Unit (Vitest)
Тестируем чистую бизнес-логику без UI:
- генерация задач математики (`add/sub`, границы до 20, `a >= b` для вычитания);
- расчет наград за урок (база, бонус за точность, серия);
- экономика (начисление/списание, запрет отрицательного баланса);
- лут (ролл по весам, дубликаты, компенсация);
- валидация world-координат и операций `place/remove`.

Цель покрытия unit:
- доменные модули: >= 90% line coverage;
- use-case функции: >= 80% line coverage.

## 3.2. Component/Integration (Testing Library + Vitest)
Тестируем React-экраны с реальным состоянием и реальными use-case/доменными модулями:
- `LessonScreen`: прохождение мини-урока и начисление валюты;
- `EggsScreen`: покупка яйца, выдача FPV-награды, сообщение о результате;
- `BuildScreen`: выбор блока, установка/удаление, расход инвентаря;
- `ShopScreen`: покупка при достаточном и недостаточном балансе;
- роутинг и базовая навигация App Shell.
- `BuildScreen hotbar`: слот 1 = ластик, автовыбор первого ресурсного слота, поведение пустого слота 2 при пустом инвентаре.

Цель покрытия component/integration:
- критичные экраны MVP: >= 70% line coverage.

## 3.4. Правило \"без имитации вместо функционала\"
- В тестах обязательно вызывать реальный код проекта (доменные сервисы, use-case, стор, UI-обработчики).
- Запрещено заменять тестируемый модуль на мок/заглушку, если его можно вызвать напрямую.
- Допустимо мокать только внешние границы:
  - сеть/HTTP;
  - браузерные API, отсутствующие в тестовой среде;
  - системное время, RNG, генератор ID (для детерминизма).
- При любом моке в PR должно быть краткое объяснение, почему без него тест невозможен или нестабилен.

## 3.3. E2E (Playwright)
Минимальный стабильный набор для релизной уверенности:
1. `happy-path-mvp`
- пройти урок;
- получить кото-монетки;
- купить яйцо;
- получить FPV-блок;
- поставить блок в мире;
- перезагрузить страницу;
- проверить восстановление прогресса.

2. `economy-guardrails`
- попытка купить яйцо без средств;
- баланс не уходит в минус;
- UI показывает корректную ошибку.

3. `touch-tablet-core`
- tablet viewport;
- открыть урок, магазин/яйца, вернуться в FPV;
- выполнить базовое действие строительства.

4. `persistence-reopen`
- серия действий (урок + яйцо + стройка), закрытие/открытие контекста;
- проверка, что данные в IndexedDB восстановлены корректно.
- отдельная проверка: блок, поставленный непосредственно перед закрытием вкладки, восстанавливается из LocalStorage-снимка, если IndexedDB не успела записаться.

## 4. Что именно считаем "критичным" в MVP
Обязательные инварианты, которые должны быть тестами:
- баланс кото-монеток никогда не отрицательный;
- награда урока начисляется один раз за сессию;
- награда яйца в MVP всегда применима в FPV-строительстве (тип `block`);
- блок нельзя поставить без ресурса в инвентаре;
- прогресс сохраняется и восстанавливается из IndexedDB.
- слот 1 hotbar всегда выполняет удаление блока;
- при пустом инвентаре активен пустой слот 2 и ЛКМ не выполняет действие.
- удаление блока ластиком возвращает ресурс в соответствующий слот инвентаря и увеличивает остаток.

## 5. Тестовые данные и фикстуры
Рекомендуется завести:
- `src/tests/fixtures/catalogs/*.json` (egg/loot/shop/math);
- `src/tests/fixtures/player/*.json` (баланс, инвентарь, мир);
- фабрики сущностей: `makePlayer`, `makeLessonSession`, `makeWorld`.

Правила фикстур:
- короткие и читаемые;
- отдельные фикстуры для edge-cases (0 валюты, пустой инвентарь, дубликаты лута);
- не переиспользовать один "гигантский" fixture для всех сценариев.

## 6. Детерминизм: random/time/id
Чтобы тесты не флапали:
- RNG инжектируется через интерфейс (`rng.next()`), в тестах подменяется seed-генератором;
- время через абстракцию (`now()`), в тестах фиксируется;
- ID через провайдер (`idProvider.next()`), в тестах предсказуемые значения.

Для лута:
- unit-тесты на фиксированных последовательностях RNG;
- отдельный статистический тест (не в каждом CI) на распределение весов.

## 7. IndexedDB и persistence тесты
- Unit для репозиториев на `fake-indexeddb`.
- Integration: проверка полного цикла `запись -> reload state -> чтение`.
- E2E: проверка, что после перезагрузки браузера состояние совпадает с ожидаемым.

Ключевые проверки:
- автосохранение после `completeLesson/openEgg/placeBlock/removeBlock`;
- синхронная запись LocalStorage-снимка после каждого изменения `world`;
- консистентность (нет отрицательных количеств/баланса);
- миграции схемы при повышении версии DB.

## 8. FPV/3D и UI тесты
- Бизнес-правила строительства тестировать на уровне домена/store, а не через пиксели.
- Для 3D-canvas в component-тестах проверять команды/события, а не визуальный рендер.
- Для e2e достаточно smoke-проверок взаимодействия (наведение курсора, установка блока, удержание ПКМ для free camera view).
- Отдельный тест на превью установки: рамка показывает именно ту клетку, куда блок встанет по клику.
- Отдельный тест на визуальную форму рамки: только ребра, без диагональных линий на гранях.

## 9. Кроссплатформенная матрица
Обязательная матрица перед релизом MVP:
- Desktop Chromium (mouse+keyboard);
- Tablet viewport (touch эмуляция в Playwright);
- Дополнительно вручную: Android-планшет (реальный smoke).

## 10. CI-гейты
Рекомендуемый pipeline (GitHub Actions):
1. `typecheck` (`tsc -b --noEmit`)
2. `lint`
3. `unit`
4. `component`
5. `e2e-smoke` (на PR)
6. `e2e-full` (nightly/main)

Merge в `main` разрешать только при успешном прохождении обязательных шагов 1-5.

## 11. Набор npm-скриптов
Рекомендуемые скрипты:
- `test`: запуск unit + component;
- `test:unit`;
- `test:component`;
- `test:e2e:smoke`;
- `test:e2e:full`;
- `test:coverage`.

## 12. Приоритизация внедрения
Порядок внедрения тестов:
1. Unit для математики/экономики/лута.
2. Component для `LessonScreen`, `EggsScreen`, `BuildScreen`.
3. E2E `happy-path-mvp`.
4. Persistence тесты (fake-indexeddb + e2e reopen).
5. Touch/tablet e2e smoke.

## 13. Критерии готовности тестовой системы для MVP
Система тестирования для MVP считается достаточной, если:
1. Критичные инварианты покрыты автоматическими тестами.
2. Есть минимум 1 стабильный сквозной e2e-сценарий полного цикла.
3. CI блокирует merge при падении lint/typecheck/test.
4. Есть отдельные проверки сохранения и восстановления прогресса.
